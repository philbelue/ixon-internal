The point of this plan

“The goal is not to make Max more important. The goal is to make the organization less dependent on Max, Brandon, Phil, and tribal knowledge.”

The operating layer converts knowledge held by individuals into repeatable systems, assets, standards, and processes. The role exists to support the operating system — the operating system does not exist to support the role.
01

Executive Summary

North America is adding people faster than it is adding systems. A local Support Engineer is being hired, SE #2 will follow, six AEs are at staggered ramp stages, the install base is growing, support volume is growing, and the product portfolio is becoming more technical — all six time zones from HQ. The systems those people need to be effective — onboarding, escalation standards, enablement, demo infrastructure, structured HQ feedback — do not exist yet. This plan builds them between July 1 and December 31.

The problem

The org runs on tribal knowledge.

Questions route to whoever knows the answer. Escalations route inconsistently. Every new hire makes it worse, not better.

The plan

Build the technical operating layer.

Six months, six workhorse assets per gate, three gates. Knowledge moves from people into systems, standards, and playbooks.

The operator

Max builds the initial version; the organization runs on it.

Max is the initial operator of the build — with a hiring-gated work split and accountability through milestone gates, not a static 70/30.

Why now? One box.

  • Six-hour HQ time difference — NA is on its own every afternoon
  • New Support Engineer landing in July
  • Future SE #2 to hire and ramp
  • Six AEs requiring technical enablement
  • Growing install base and support volume
  • Technical complexity increasing

Risks if we do nothing

  • New hires ramp slowly and absorb senior attention instead of creating leverage.
  • Escalations continue routing inconsistently, especially outside the HQ overlap window.
  • Technical load remains concentrated in a few people instead of moving into systems.
  • HQ continues receiving uneven field signal instead of clean, packaged technical feedback.

The Technical Operating Layer

The operating layer is not a person — it is a tiered system that gives every request a first move before it consumes a senior human. Each tier deflects what it can and passes only what it must.

TIER 0Self-service
Knowledge base · FAQs · playbooks · demo guides · qualification checklists
Deflects routine questions
TIER 1Function owner
AE: discovery · SE: pre-sales proof · CSE: adoption & implementation · Support: tickets & first-line triage
Keeps ownership in the right lane
TIER 2Operating layer gate
Ambiguity · cross-functional issues · escalation quality · standards · coaching against the playbook
Resolves what only judgment can
TIER 3HQ / Technical / Eng.
Only complete, structured escalations: context, root cause, impact, recommended next step
Receives signal, not noise
Design rule — externalization Every recurring answer becomes an FAQ entry. Every recurring demo becomes an environment. Every recurring ramp becomes curriculum. Every recurring escalation becomes a routing rule. The layer continuously converts individual knowledge into organizational assets — that is the entire mechanism by which dependence on individuals decreases.

July–December Roadmap

This is the plan’s centerpiece. The roadmap is the proof, the transition, and the operating plan — everything else in this document supports it. Three build outputs per month; the full backlog lives in the working tracker.

The build, month by month

Six months. Eighteen outputs. One operating system.

Each month ends with a definition of done. Months 1–2 put foundations under the new Support Engineer. Months 3–4 make the system repeatable and visible. Months 5–6 stress-test it and write it down.

Month 1 · July
Baseline & charter
  • Role charter + decision rights v1
  • Support Engineer ramp plan
  • SE / CSE / Support ownership matrix
Done = everyone agrees what Max owns, influences, and does not own.
Month 2 · August
Routing & enablement v1
  • Escalation matrix v1
  • Knowledge base / technical FAQ v1
  • Enablement library + first core demo standard
Done = routine questions have a first destination that is not a person.
Month 3 · September
Onboarding & repeatability
  • 30/60/90 technical onboarding + certification path
  • Demo environment library v1
  • AE self-service cadence (office hours + FAQ growth)
Done = new hires and AEs train from a path, not from one-off explanations.
Month 4 · October
Operating rhythm
  • Weekly triage cadence + technical dashboard v1
  • Support routing / handoff SOP published
  • HQ feedback loop v1 (monthly packaged report)
Done = leadership can see where friction comes from and whether it is improving.
Month 5 · November
Scale test
  • Support ramp checkpoint + refinement from real patterns
  • SE #2 ramp active (if hired)
  • HQ technical working session
Done = the system is stress-tested against real sales, support, and onboarding load.
Month 6 · December
Playbook & review
  • NA Technical Operating Playbook v1
  • Steady-state review + January split recommendation
  • 2027 readiness recommendation
Done = the operating layer exists outside Max’s head and can be evaluated.

Recommendation

Before the recommendation — the one thing to hold onto

“The goal of the July–December build phase is not to create a stronger dependency on Max. The goal is to create a stronger technical organization with less dependency on any individual.”

Brandon’s role definition should be accepted as the desired end-state. However, July–December should be formally recognized as a build phase. The primary objective of this period is not operating the technical organization — it is building the technical operating system that allows the organization to scale. The role should be evaluated on build-phase outputs and milestone completion, not a static 70/30 assumption. The December review then sets the January steady state — split, rhythm, and role — from six months of evidence.

Final word

“IXON should not confuse Max helping across teams with Max building the infrastructure that allows those teams to scale.”
